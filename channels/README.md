# channels — 유튜브 채널 관측 (경제·부동산·도시개발)

> **상태: 2주 타당성 검증 중.** 앱이 아니다. 2026-10-20 시작.
> 판정 질문은 하나다 — **성장 순위가 매일 요동치는가.** 안 요동치면 첫 화면이 고정되고
> 재방문이 0이 되므로 거기서 접는다.

## 왜 하루라도 빨리 시작하나

**유튜브 API 는 *현재* 값만 준다.** 과거 추이는 어디서도 살 수 없고 소급해서 만들 수도 없다.
오늘 안 찍은 날은 영구히 빈다. 쌓이는 series 자체가 자산이고, 앱은 그 위에 얹는 화면이다.
→ 그래서 `snapshot.py` 가 워크플로의 **첫 단계**이고, 뒤 단계가 쿼터를 먹어도 series 는 남는다.

## 🚨 구독자수로 성장을 재지 말 것

`subscriberCount` 는 1,000명 이상 채널에서 **유효숫자 3자리로 반올림**돼 온다
(123,456 → `123000`). 큰 채널은 일간 증감이 반올림에 먹혀 **0으로 보인다.**
"구독자 급상승 랭킹" 으로 갔다면 2주 뒤에 "데이터가 안 움직인다" 는 잘못된 결론이 나왔다.

| 쓸 것 | 성질 |
|---|---|
| `viewCount` 일간 증가분 | **정확하다.** 주 지표. 주식의 거래량에 대응한다 |
| `videoCount` 변화 | 업로드 감지. 연속 업로드 일수·휴면 판정이 **추가 쿼터 0원** |
| `subscriberCount` | 반올림. **규모 구간용으로만** |

## 쿼터 배분 (기본 10,000/day · 태평양시 자정 리셋)

| 단계 | 비용 | 비고 |
|---|---|---|
| 스냅샷 `snapshot.py` | 채널 50개당 1 — 5,000채널에 ~100 | 제약이 아니다 |
| 발굴 `discover.py`·씨앗 `resolve.py` | search 1회 100 · **하루 60회 상한** | 유일한 병목 |
| 길이구간 `uploads.py` | 채널당 ~2 · 예산 2,500 | 🚧 **2주 검증 동안 CI 에서 끔** |

**상한을 올리기 전에 이 표를 다시 계산할 것.** 넘기면 그날 스냅샷이 같이 죽는다.
장부는 `.quota/<태평양날짜>.json` — 🚨 KST 로 끊으면 하루가 어긋나 상한이 풀린다.

## 🚧 2주 검증 동안의 설정 (2026-10-20)

- **영상 단위 수집을 껐다.** 판정 지표가 채널 스냅샷에서 나오므로 필요 없다.
  그 예산을 발굴로 돌려 `PER_RUN` 을 6 → **50 질의/일** 로 올렸다 (질의 76줄 = 1.5일에 한 바퀴).
- **카테고리는 「깊게」로 정했다** — 먹방·브이로그로 넓히는 대신 경제 안에서 세분화한다
  (macro·kr-stock·us-stock·etf·dividend·pension·tax·personal·crypto·biz, 부동산 6, 도시 4).
  넓은 쪽은 플레이보드·유튜브 추천이 가장 강하고 **분류 노동이 선형으로 는다.**
  `queries.tsv` 맨 아래에 주석으로 남겨 뒀다 — 판정 통과 뒤 풀면 된다.

🚨 **장부는 로컬과 CI 가 따로 센다.** 같은 날 둘 다 돌리면 합계가 10,000 을 넘을 수 있다.
   CI 가 매일 05:10 KST 에 도니, 로컬 실행은 그 전후로 피한다.

## 분류는 우리가 한다

유튜브 `videoCategory` 는 15개 내외로 거칠어 **경제·부동산·도시개발이 없다.**
씨앗은 손으로 라벨을 달고(`classifiedBy: hand`), 발굴된 채널은 `category: null` 로 들어와
`pending-classify.tsv` 에 쌓인다. 질의 카테고리는 **힌트일 뿐**이다 — "부동산" 검색에
부동산 아닌 채널이 섞여 오고, **그걸 걸러낸 이력이 자산이다.**

## 파일

| 경로 | 내용 |
|---|---|
| `registry.json` | 채널 대장 — 분류·등급(active/dormant)·연속 업로드·최근값 |
| `series/<날짜>.jsonl` | 일간 스냅샷. `{d,id,s(구독),v(조회),n(영상수)}` |
| `videos/<날짜>.jsonl` | 최근 7일 영상별. `{ch,vid,pub,sec,form,v,l}` · `form`=길이구간 |
| `needs-review.tsv` | **검수 대기** — 이름으로 찾은 채널. 오염의 유일한 입구 |
| `pending-classify.tsv` | 분류 대기 — 발굴된 채널 |
| `discover-state.json`·`uploads-state.json` | 커서. "매일 조금씩" 의 기억장치 |

## 알고 쓰는 한계

- **"쇼츠" 라고 쓰지 않는다.** API 에 `isShort` 가 없다. 대신 **길이 구간**으로 적는다 —
  `lt1m`(60초 미만 · 사실상 쇼츠) · `lt3m`(1~3분 · 섞인다) · `ge3m`(롱폼).
  화면에도 "3분 미만 / 1분 미만" 으로 쓴다. 2분짜리 일반 영상을 쇼츠라고 표시하면
  틀린 것이지만 "3분 미만" 은 틀릴 수 없다 (BRAND.md 3번).
  확정하려면 `youtube.com/shorts/{id}` 가 리다이렉트 없이 열리는지 봐야 하는데 API 밖이다.
- **업로드 감지는 하루 1회로 뭉친다.** 하루에 2개 올리면 1회, 영상을 지우면 감소한다
  (감소는 업로드로 세지 않는다).
- **휴면(30일 무업로드)은 주 1회만 찍는다.** 쿼터를 버는 유일한 정직한 방법이다.

## 하지 않기로 한 것 — 수익 추정 (2026-10-20 결정)

길이로 가르면 추정은 **가능하다.** 그래도 넣지 않는다:
1. **RPM 을 관측할 수 없다.** 쇼츠는 롱폼의 수십분의 1이고 경제·부동산은 RPM 축이 가장
   높아 편차가 크다 → 구간으로만 쓸 수 있는데, BRAND.md 3번(불확실한 값을 자신 있게
   보여주는 것이 가장 큰 신뢰 손상)과 부딪힌다.
2. API 정책에 **revenue 인사이트 목적의 집계 금지** 조항이 있다. 36개월 보관 승인을
   받아야 하는 입장에서 먼저 긁을 자리가 아니다.

## 돌리는 법

```bash
# 키: ~/.config/stock-tools/youtube.env 에 YOUTUBE_API_KEY=... 한 줄 + chmod 600
#     (CI 는 허브 저장소 Secrets 의 YOUTUBE_API_KEY)
python3 scripts/channels/resolve.py    # 씨앗 → 레지스트리 (며칠에 걸쳐 끝난다)
python3 scripts/channels/snapshot.py   # 매일. 이게 본체다
python3 scripts/channels/discover.py   # 발굴 (질의 커서)
python3 scripts/channels/uploads.py    # 쇼츠/롱폼
python3 scripts/channels/analyze.py    # 2주 뒤 판정
```

CI 는 `.github/workflows/fetch-channels.yml` — 매일 05:10 KST (쿼터 리셋 뒤).
