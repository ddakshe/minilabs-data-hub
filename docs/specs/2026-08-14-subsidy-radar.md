# subsidy-radar 생애이벤트 기반 지원금 타이밍 (spec)

> ## ⏸ 보류 (2026-08-14)
>
> **설계 완료, 개발 중단.** 스크래퍼(`scripts/fetch-subsidy.mjs`)는 작성하지 않았다.
>
> 보류 사유 — 재방문 동력이 성립하지 않는다고 판단:
>
> 1. **저빈도** — 보조금 탐색은 연 1~2회
> 2. **미니앱에는 검색 유입이 없다** — 이벤트 큐레이션(B)을 택한 근거가 "저빈도지만 검색 유입이 강하다"였는데, 토스 미니앱은 웹 검색이 아니라 토스 앱 내부 노출로 발견된다. **저빈도를 감수한 대가가 이 채널에는 애초에 존재하지 않는다.** 11장의 "검색 유입·공유로 보완"은 채널을 고려하지 않은 서술이었다
> 3. **본체 중복** — 토스에 정부지원금 조회 기능 존재. 증여세·상속세 앱의 "카테고리 부적합" 거절과 같은 성격
> 4. 재방문이 기능 5 하나에 의존하며, 그 전제(주간 신규 유입량)는 **끝까지 미검증**
> 5. 차별점이 "인증 없이 대략" — 정확도를 포기한 열등 버전으로도 읽힌다
>
> **재개 조건:** 활용신청 승인 후 `serviceList`를 2주간 저장해 주간 신규 유입 건수를 실측(10장 검증 7번). 주당 수십 건이면 기능 5가 성립하므로 재검토할 가치가 있다. 한 자릿수면 접는다. 이 확인은 파이프라인 없이 20줄 스크립트로 가능하다.
>
> **보존된 산출물:** 이 스펙, `subsidy-radar-mini/`(화면 5개·테스트 24개 통과·빌드 통과), 3장의 odcloud 진단법, 5장 JA 코드 매핑, 7장 필드 매핑.

- 작성일: 2026-08-14
- 대상 파이프라인: `minilabs-data-hub` → `scripts/fetch-subsidy.mjs` + `subsidy/*.json`
- 소비자: `subsidy-radar-mini` (앱인토스 WebView), GitHub raw로 JSON 소비

## 1. 배경 / 문제

출발점은 `행정안전부_통계연보_보조금24`(data.go.kr 15107424)였다. 실측 결과 이 API는 앱 재료가 아니다.

- 엔드포인트: `https://apis.data.go.kr/1741000/Subsidy24/getSubsidy24` (오퍼레이션명 없이 `/Subsidy24`만 호출하면 `NO_OPENAPI_SERVICE_ERROR`)
- 전량 76행 = 4개 연도(2021~2024) × 19개 지역(계 + 17개 시도 + 기타)
- 필드: `wrttimeid`(연도), `cls`(지역), `tot`(총 이용건수), `online_use_cnt`/`online_rate`, `visit_use_cnt`/`visit_rate`

**보조금의 이름·금액·자격요건이 한 항목도 없다.** 보조금24라는 서비스의 이용 실적 집계표일 뿐이다. 76행 정적 데이터에는 사용자 재방문 이유가 존재하지 않는다.

실제 콘텐츠는 별도 API에 있다: `행정안전부_대한민국 공공서비스(혜택) 정보`(15113968). 경로 실재를 확인했다 — 미등록 키로 호출 시 `{"code":-4,"msg":"등록되지 않은 인증키 입니다."}`가 오는데, 이는 경로가 유효하고 활용신청만 안 된 상태를 뜻한다(경로가 틀리면 404 계열이 온다).

### 통계연보의 올바른 용도

폐기하지 않는다. **사용자에게 보여줄 콘텐츠가 아니라, 지자체 커버리지 확장 우선순위를 정하는 내부 의사결정 데이터**로 쓴다.

| 연도 | 계 | 수도권(서울+경기+인천) | 비중 |
|---|---|---|---|
| 2022 | 4,544,267 | 2,305,836 | 50.7% |
| 2023 | 2,919,309 | 1,511,725 | 51.8% |
| 2024 | 1,773,222 | 904,180 | 51.0% |

수도권 3개만으로 전체 이용의 약 51%를 커버하며, 3년간 비중이 안정적이다. 확장 순서(2024 기준 누적): 경기 26.0% → 서울 43.3% → 인천 51.0% → 부산 57.5% → 경남 63.5% → 대구 68.1% → 경북 72.6% → 충남 76.7%.

**주의: `tot` 절대값은 신뢰하지 않는다.** 2021년 `계`가 25,616,566인데 17개 시도 합은 약 250만으로, 자릿수 하나가 틀린 원본 오류다. 연도별 총량도 454만→292만→177만으로 급감하는데 이는 이용 감소가 아니라 집계 기준 변경으로 보인다. **비율만 사용한다.**

## 2. 목표 / 비목표

**목표**
- 포지셔닝을 "조회"가 아닌 **"타이밍"** 으로 잡는다. 토스 본체는 인증 후 "내가 받을 수 있는 것"을 보여주고, 이 앱은 "지금이 신청할 때인 것"을 보여준다.
- 생애이벤트를 진입점으로 삼아 7,500개 중 지금 내게 해당하는 것만 노출.
- 신규 공고 / 마감 임박을 감지해 반복 방문 이유를 만든다.

**비목표**
- 신청 대행. 신청은 정부24 원문으로 이관한다.
- 지원금액 합산·비교. 원문이 서술형 텍스트라 정확도를 보장할 수 없다.
- 본인인증 기반 정밀 자격 판정. 익명 후보 좁히기까지만 한다.
- 전국 지자체 전수 커버(1단계 범위 밖, 4장 참조).

### odcloud 에러코드 진단법 (2026-08-14 실측)

`api.odcloud.kr`는 경로 오류와 권한 오류를 다른 코드로 구분한다. 스크래퍼 장애 시 원인 분리에 사용한다.

| 응답 | 의미 |
|---|---|
| `HTTP 401` / `{"code":-4,"msg":"등록되지 않은 인증키 입니다."}` | **경로는 유효, 키가 해당 데이터셋에 미등록** |
| `HTTP 404` / `{"code":-3,"msg":"등록되지 않은 서비스 입니다."}` | 경로 자체가 존재하지 않음 |

이 대조로 `gov24/v3/serviceList`와 `gov24/v3/supportConditions` **경로 유효성은 확인 완료**(401 반환). 남은 것은 활용신청 승인뿐이다.

키 인코딩은 원인이 아니다 — 인코딩키/디코딩키/`Authorization: Infuser` 헤더 3가지 모두 동일하게 `-4`를 반환했고, 같은 키로 `Subsidy24`는 정상 응답한다.

주의: 이름이 유사한 데이터셋이 다수 존재한다. 필요한 것은 **`행정안전부_대한민국 공공서비스(혜택) 정보` (15113968)** 이며, `행정안전부_대한민국 공공서비스 정보(보조금24)`는 별개다.

**런타임 호출 불가.** 개발계정 트래픽이 10,000/일이라 앱에서 직접 API를 호출하면 즉시 한도 초과한다. 기존 도메인과 동일하게 **스크래퍼 → 정적 JSON 스냅샷 → GitHub raw** 구조가 유일한 선택지다.

## 4. 커버리지 범위

1단계는 **중앙부처 전수 + 지자체는 수도권(서울·경기·인천)만**.

근거: 데이터 품질 편차와 분류 노동이 지자체에서 급증하는데, 수도권 3개로 이용의 51%를 커버할 수 있다(1장). 이후 부산·경남 순으로 단계 확장한다.

**API에 생애이벤트 태그는 없다.** 직접 만들어야 하며, 이것이 이 프로젝트의 실제 노동 대부분이자 경쟁 앱이 복제하기 어려운 유일한 자산이다.

|---|---|---|
| `birth` | 아이가 생겼다 | 임신·출산·양육 조건코드 |
| `housing` | 이사했다 / 집을 구한다 | 주거·전월세 |
| `joblost` | 일을 잃었다 | 실업·구직 |
| `employed` | 취업했다 / 첫 직장 | 청년·근로 연령코드 |
| `startup` | 창업했다 | 소상공인·사업자 |
| `illness` | 아프다 / 간병한다 | 의료·돌봄 |

### JA 코드 매핑 (2026-08-14 OAS 실측 확정)

`supportConditions`는 50개 필드 전부에 의미 설명이 붙어 있으며, **8개 이벤트가 모두 JA 코드에 직접 대응한다.**

| 이벤트 | 매칭 코드 |
|---|---|
| `birth` | JA0301 예비부모/난임, JA0302 임산부, JA0303 출산/입양, JA0411 다자녀가구 |
| `housing` | JA0412 무주택세대, JA0413 신규전입 |
| `joblost` | JA0327 구직자/실업자, JA1103 생계곤란/폐업예정자 |
| `employed` | JA0326 근로자/직장인 |
| `startup` | JA1101 예비창업자, JA1102 영업중, JA1201·1202·1299 업종 |
| `illness` | JA0330 질병/질환자, JA0328 장애인 |
| `learning` | JA0317 초등학생, JA0318 중학생, JA0319 고등학생, JA0320 대학생/대학원생 |
| `aging` | JA0110/JA0111 대상연령 범위 |

기타 활용 가능 축: JA0101/0102 성별, JA0201~0205 중위소득 구간, JA0401~0404 가구유형(다문화·북한이탈·한부모·1인가구), JA2101~2103 기관유형.

### 분류 2단계

1. **자격조건 코드 규칙 (결정론적, 주력)** — 위 매핑으로 확정. 재현 가능하고 비용 0이며 날짜별 흔들림이 없다.
2. **LLM 보완 (진짜 폴백)** — JA 코드가 비어 있는 잔여분만 서비스명·지원내용으로 분류.

당초 LLM을 주력으로 가정했으나 OAS 확인 결과 코드 커버리지가 높아 **주력과 폴백이 뒤바뀌었다.** 2단계 착수 시 코드 규칙만으로 몇 %가 태깅되는지 먼저 실측하고, 잔여분이 적으면 LLM 단계를 생략할 수도 있다.

**LLM 분류 결과는 서비스ID 기준으로 태그 캐시에 커밋한다.** 이유:
- 매일 cron이 도는데 매번 LLM을 재호출하면 비용이 선형 증가한다.
- 더 심각하게는, 같은 보조금이 날마다 다른 이벤트로 분류되어 사용자가 보는 결과가 흔들린다.

캐시가 있으면 신규 서비스만 LLM을 타므로 비용이 0에 수렴하고 분류가 안정된다. 태그 캐시는 리포지토리에 커밋되어 사람이 검수·수정할 수 있다(오분류 수동 교정 경로).

한 서비스는 복수 이벤트에 속할 수 있다(예: 청년 주거지원 → `housing` + `employed`).

## 6. 파이프라인

```
gov24 serviceList + supportConditions 전량 페이징
        ↓  raw 스냅샷 보존
정규화 → 범위 필터 (중앙부처 전체 + 서울·경기·인천)
        ↓
이벤트 태깅  (a) 조건코드 규칙  (b) 잔여만 LLM → 태그 캐시 커밋
        ↓
diff(어제 ID집합, 오늘 ID집합) → isNew / firstSeenAt
        ↓
subsidy/services.json  +  subsidy/by-event.json
```

- 워크플로: `.github/workflows/fetch-subsidy.yml`, 일 1회
- 스크립트: `scripts/fetch-subsidy.mjs`
- 인증키: 기존 도메인과 동일하게 GitHub Secrets

### 지역 판별 (구현 부담 주의)

**API에 지역 코드 필드가 없다.** `소관기관명`·`소관기관코드`·`소관기관유형`뿐이므로 지역은 **기관명 문자열에서 파싱**해야 한다 (예: `성남시` → 경기, `서울특별시 강남구` → 서울).

- `소관기관유형`으로 중앙부처/지자체를 먼저 가른다
- 지자체는 기관명 → 시도 매핑 테이블을 직접 관리한다
- 매핑 실패 건은 버리지 않고 `region: unknown`으로 두되 건수를 로그로 남긴다 (9장 게이트)

`subsidy/by-event.json` — 이벤트 키 → 서비스ID 배열 인덱스.

1~2천 건 규모이므로 단일 파일 + gzip으로 충분하다. 상세 분할 불필요.

### `deadline` 부재 시 폴백

`deadline`이 채워지지 않을 가능성이 있다(10장). **`firstSeenAt`이 보험이다.** 신청기간 필드가 비어 있어도 "우리가 언제 처음 봤는가"는 우리가 생성하는 사실이므로, 정렬을 다음으로 이원화한다.

- `deadline` 있음 → D-day 정렬
- `deadline` 없음 → `firstSeenAt` 기준 "최근 추가" 정렬 + `isNew` 배지

이로써 A(타이밍)는 미검증 필드에 의존하지 않는다.

## 8. 앱 구조

```
진입  →  "지금 내게 일어난 일" 이벤트 8칸 그리드
                    ↓
        이벤트별 지원금 리스트 (신규·마감임박 우선 정렬)
                    ↓
        요약 카드  →  정부24 원문 딥링크로 이관

상시 탭 →  "이번 주 새로 생긴 지원금" (스냅샷 diff)
지역    →  최초 1회 시군구 선택 후 localStorage (중앙부처는 항상 포함)
```

**신청은 앱에서 처리하지 않고 정부24로 넘긴다.** UX 타협이 아니라 방어선이다. 신청 대행으로 읽히면 심사 리스크와 법적 책임이 동시에 발생한다.

스택은 기존 미니앱과 동일: Vite + React + CSS.

### v1 기능 범위 (확정, 7개)

| # | 기능 | 비고 |
|---|---|---|
| 1 | 생애이벤트 8칸 그리드로 진입 | 5장 이벤트 키 |
| 2 | 지역 필터 (최초 1회 **시/도** 선택, localStorage) | 중앙부처 항상 포함, 지자체는 내 지역만 |
| 3 | `NEW` 배지 (최근 7일 내 신규) | `isNew` |
| 4 | 마감 D-day 정렬 | `deadline` 없으면 `firstSeenAt` 순 (7장 폴백) |
| 5 | "이번 주 새로 생긴 지원금" 상시 탭 | **재방문을 만드는 유일한 기능** |
| 6 | 요약 카드 (서비스명·지원내용·소관기관·마감일) | 원문 그대로, 가공 없음 |
| 7 | 정부24 원문 바로가기 | 신청 이관 |

이 목록이 v1 전부다. 기능 개수가 아니라 **"내 상황에 맞는 N건"의 정확도**가 가치를 결정하므로, 개발 노동은 화면이 아니라 5장(이벤트 분류)에 집중된다.

### v1에서 의도적으로 제외

| 제외 | 이유 |
|---|---|
| 본인인증 기반 자격 판정 | 인증 없는 것이 차별점. 정밀 판정은 정부24의 역할 |
| 금액 계산·합산 | 원문이 서술형 텍스트. 숫자화하면 틀린 금액을 노출하게 됨 (9장) |
| 신청 대행 | 심사·법적 책임 리스크 |
| 전국 지자체 커버 | 1단계는 수도권만 (4장) |

### UI 결정 (2026-08-14, Stitch 시안 검토 반영)

디자인 시스템은 Stitch 산출물 `Civic Trust System`을 채택한다 (Government Blue `#003366`, Public Sans + Noto Sans, 4px 베이스라인, 카드 radius 8px). 원본: `stitch_/civic_trust_system/DESIGN.md` + 각 화면 `code.html`.

**채택**

- 배지 3종: `신규` / `마감임박` / **`진행중`**. `진행중`은 `신청기한`이 비어 있는 상시모집 건의 표현으로 사용한다 (7장 폴백의 UI 표현).
- 신규 탭의 상대 시간 표기: "오늘 등록됨 / 어제 등록됨 / N일 전 등록됨". `firstSeenAt`을 사용자 언어로 노출하는 방식.
- 상세 화면 구성: 지원내용 / 지원대상 / 신청방법 / 마감일 + 하단 고정 "정부24에서 신청하기".

**수정**

| # | 시안 | 결정 | 이유 |
|---|---|---|---|
| 1 | 시/도 + 시/군/구 2단 선택 | **시/도까지만** | 지역 필드가 없어 `소관기관명` 파싱으로 추정한다(7장). 시군구 단위 정확도를 보장할 수 없다 |
| 2 | 17개 시도 모두 선택 가능 | **미지원 지역은 비활성 + "준비 중"** | 1단계는 수도권만(4장). 선택 후 0건은 최악의 첫인상 |
| 3 | 하단 탭에 `Profile` | **제거** | v1에 계정이 없고 인증 없음이 차별점이다. 로그인을 암시하면 포지셔닝과 충돌 |
| 4 | 하단 탭에 `Search` | **v1 제외** | 확정 기능 7개 밖. v2 후보 |
| 5 | 탭 라벨 영문 | **한국어** | 고령 사용자 포함 |
| 6 | 소관기관명이 카드 우상단에 잘림 | **제자리 배치** | 신뢰도에 직결되는 정보 |

**금지**

DESIGN.md는 Success Green을 `Active` / **`Eligible`** / `Approved`에 쓰라고 기술하지만, **사용자 자격을 뜻하는 표시에는 절대 사용하지 않는다.** 자격 판정은 v1 비목표이며(위 "의도적으로 제외"), 인증 없이 "받을 수 있음"을 표시하면 필연적으로 틀린다. 초록색은 `진행중` 같은 **공고 자체의 상태**에만 쓴다.

### 알려진 약점

재방문 동력이 기능 5 하나에 전적으로 의존한다. **주간 신규 유입 건수가 낮으면 이 앱의 빈도 전제가 무너진다.** 10장 검증 시 신규 공고 유입률을 반드시 실측해야 하며, 주당 유입이 한 자릿수면 앱 구조를 재검토한다.

## 10. 미검증 의존성

### 해결됨 (2026-08-14, OAS로 확인)

15113968의 공식 스웨거는 **`https://infuser.odcloud.kr/api/stages/44436/api-docs`** 이다. `data.go.kr/data/15113968/openapi.do` HTML에서 추출했다. 이 주소는 **인증 없이 열람 가능**하므로 활용신청 승인과 무관하게 명세를 읽을 수 있다.

- ~~필드명과 구조~~ → 7장에 매핑 확정
- ~~신청기간 필드 존재 여부~~ → `신청기한` 실재 확인
- ~~코드 체계~~ → 5장에 JA 코드 50종 매핑 확정. 규칙 분류가 주력으로 승격

`infuser.odcloud.kr/oas/docs?namespace=...` 경로는 이 데이터셋에 대해 쓸모없다(`APPLICATION_001`). `stages/<id>/api-docs`가 유효한 경로다.

### 남은 검증 (실데이터 필요)

1. **`신청기한` 채움률** — 낮으면 7장 `firstSeenAt` 폴백으로 전환
2. **JA 코드 태깅 커버리지** — 규칙만으로 몇 %가 분류되는지. 높으면 5장 LLM 단계 생략
3. **`소관기관명` → 시도 파싱 성공률** — 7장 지역 판별의 실현 가능성
4. 지자체 데이터 품질 편차 — 4장 범위 재검토
5. 이벤트 8개별 실제 서비스 건수 — 얇은 이벤트 통폐합 판단
6. 전체 건수와 응답 크기 — 7장 단일 파일 전략 유효성
7. **주간 신규 공고 유입 건수** — 8장 기능 5(재방문 동력)의 전제. 스냅샷 2주치를 쌓아 diff 실측. 주당 한 자릿수면 앱 구조 재검토

### 현재 차단 상태

`serviceKey`가 15113968에 등록되지 않아 세 오퍼레이션 모두 `HTTP 401 / code -4`를 반환한다 (2026-08-14 09:58 기준). 확인된 사실:

- 키 자체는 유효 — 같은 키로 `Subsidy24`는 정상 응답
- 경로는 정확 — OAS가 명시한 경로와 일치
- 인코딩 무관 — 인코딩키/디코딩키/`Authorization` 헤더 모두 동일 결과
- v1·v2는 폐기(`-3`), v3만 생존

활용신청은 계정 소유자만 가능하다: https://www.data.go.kr/data/15113968/openapi.do (통상 즉시 자동승인)
